> **模块四是一个基于 GraphRAG、面向多文档专题研判、证据追溯与风险智能分析的全域知识图谱平台。**

### 2.3 Ingestion 文本合成与入图准备层

## 3. 创新性解决方案

下面按照“问题 - 方案 - 效果”的方式，归纳模块四在知识图谱与图谱智能检索上的创新点。这里的论证结合了模块四源码实现与 GraphRAG / Neo4j 官方资料。

### 3.1 从“关键词命中”升级为“社区级语义研判”

**问题：**
市面上大多数文档处理软件擅长 OCR、全文检索、关键词定位，但面对“一个专题里有哪些核心主题”“哪些实体跨章节反复出现”“多份报告之间的主线是什么”这类全局性问题时，往往只能返回若干片段，缺少整体结构。

**方案：**
模块四采用 GraphRAG-first 方案，而不是把普通向量检索简单包上一层图数据库。源码中明确存在：

- 社区构建与社区报告导入
- `local / global / drift / basic` 四种检索模式
- community reports 作为重要查询上下文

这与 Microsoft GraphRAG 论文和官方文档的思路是一致的：通过实体、关系、社区和社区报告，把文档组织成更适合“全局理解”的知识结构。

**效果：**
模块四能够把“单句命中式问答”升级为“社区级摘要 + 主题路径 + 关联实体”式回答，特别适合：

- 政务统计公报解读
- 行业研究报告研判
- 医疗、环保、民生等专题文档的结构化分析

### 3.2 从“解析结果堆叠”升级为“上游抽取结果的语义重组入图”

**问题：**
很多图谱系统只把原始文档文本送进建图流程，忽略了上游解析阶段已经获得的大量有价值信号，例如结构化字段、sheet 行列、trace 命中、摘要工件、助手提炼信息。

**方案：**
模块四并不是只读取一个纯文本文件，而是通过 `text_corpus.py` 把模块二的多类工件进行语义重组，包括：

- 文本主语料
- markdown 摘要
- assistant payload
- xlsx workbook manifest
- sheet rows
- field 结果
- trace 命中证据

它不是“把模块二结果生搬硬套进模块四”，而是先做去噪、去壳、去乱码、去 display shell，再重组为更适合 GraphRAG 的高质量输入语料。

**效果：**
这使模块四的入图质量明显高于“仅原文切块”的方案，尤其对：

- 表格密集型文档
- 公报类文档
- 模块二已完成结构化抽取的文件

具有明显优势。

### 3.3 从“单一问答模式”升级为“多模式 GraphRAG 检索编排”

**问题：**
不同业务问题对检索方式要求不同：

- 有的问题需要局部精准
- 有的问题需要全局归纳
- 有的问题需要先找主题再扩散
- 有的问题只需要快速粗答

如果只有一种检索策略，就很难兼顾质量和效率。

**方案：**
模块四把查询显式拆分为四种模式：

- `local`：社区内精准检索
- `global`：跨社区全局综合
- `drift`：先全局锁定主题，再局部扩展
- `basic`：轻量快速回答

同时，源码里实现了清晰的降级链路：

- `drift -> local -> basic`
- `basic` 不可用时回退到 text units fallback

**效果：**
这使模块四具备“高质量优先，但不轻易全盘失败”的工程韧性，既能适配复杂研判，也能保证轻问答的响应。

### 3.4 从“图谱构建完成即算成功”升级为“Artifact 分阶段质量门控”

**问题：**
许多图谱链路只要能写出少量节点边就标记成功，导致后续图谱查询、社区报告、证据链路质量参差不齐。

**方案：**
模块四在导入前后都维护 artifact 分阶段状态，明确检查：

- `text_units`
- `entities`
- `relationships`
- `communities`
- `community_reports`

同时会记录：

- `full_ready`
- `partial_ready`
- 每个阶段是否存在匹配 artifact
- 命中的具体路径与文件大小

**效果：**
这使模块四不只是“能成图”，而是“知道成图成到了哪一步、哪些阶段完整、哪些阶段缺失”，便于后续排障、质量验收和增量修复。

### 3.5 从“图谱展示”升级为“证据-规则-告警一体化风险智能”

**问题：**
普通知识图谱系统通常止步于“能查节点、能看边”，但业务侧真正需要的是：

- 哪些内容值得预警
- 为什么预警
- 证据是什么
- 风险分数是多少

**方案：**
模块四把图谱查询能力与规则引擎、证据系统联动起来，形成：

- deterministic rules
- alert generation
- evidence binding
- alert ack / resolve
- explain / simulate

这意味着模块四不是纯展示型系统，而是带有“业务研判”属性的图谱智能平台。

**效果：**
在政务、医疗、环保、产业链等业务场景中，模块四能够从“图谱可视化”进一步升级为“风险识别与辅助决策”工具。

### 3.6 从“图数据库强依赖”升级为“主链路稳定、下游图投影可选”

**问题：**
如果主链路过度依赖 Neo4j 等外部图数据库，任何外部异常都可能把主图谱构建流程拖垮。

**方案：**
模块四采用 **best-effort Neo4j projection**：

- 主图谱以 PostgreSQL + GraphRAG artifacts 为核心
- Neo4j 作为下游投影与外部图浏览增强
- 投影失败不阻断主 ingest 成功

**效果：**
这让模块四兼顾了：

- 主业务链路稳定性
- 外部图生态兼容性
- 部署灵活性

### 3.7 从“黑箱图谱问答”升级为“可解释、可模拟的图谱分析”

**问题：**
很多图谱问答系统只返回一个答案，无法解释依据，也无法评估在不同假设场景下结果如何变化。

**方案：**
模块四提供：

- `Explain`：解释某个 alert 或 node 的结论依据
- `Simulate`：在给定上下文或规则范围内模拟风险命中结果

**效果：**
这让模块四更适合专家复核、领导汇报、业务沙盘推演，而不仅仅是“问一句答一句”。

### 3.8 从“单次运行”升级为“可恢复、可探测、可治理的长链路服务”

**问题：**
GraphRAG 这类长链路任务容易受数据库、模型服务、工作空间、依赖环境波动影响。如果没有良好的运行时治理，系统容易出现“能演示、不能长期跑”的问题。

**方案：**
模块四在工程层面建立了完整的治理能力：

- strict database mode
- healthz basic / deep probe
- provider / Neo4j reachability check
- in-flight job recovery
- rebuild replay
- timeout / retry / skip workflow 策略

**效果：**
这让模块四从“实验性脚本”真正迈向“可长期运行的图谱服务模块”。

## 5. 详细功能设计

## 5.1 模型与方法选择

### 5.1.1 图谱构建主方法

**当前方案：**

- 主方法：GraphRAG
- 运行模式：`graphrag`
- 可选模式：`deterministic_local`
- 当前分块参数：
  - `MODULE4_GRAPHRAG_CHUNK_SIZE=1200`
  - `MODULE4_GRAPHRAG_CHUNK_OVERLAP=100`

**为什么这样选：**

- 普通向量 RAG 更擅长局部相似片段召回，但面对“宏观总结、社区主题、结构全景”时能力有限。
- GraphRAG 把文本进一步组织成实体、关系、社区、社区报告，更适合复杂知识型问答和专题研判。
- 对模块四而言，目标不是“找一段最像的问题上下文”，而是“把文档或专题的结构骨架建立出来”，因此 GraphRAG 更合适。

**相较于直接向量检索的优势：**

- 更适合全局理解
- 更适合多实体关系表达
- 更适合形成社区级摘要
- 更适合可视化图谱展示

### 5.1.2 检索与回答方法

**当前方案：**

- `local` 检索
- `global` 检索
- `drift` 检索
- `basic` 检索

**当前模型配置：**

- Chat model：`gpt-5-mini`
- Embedding model：`gemini-embedding-001`

**为什么这样选：**

- `local` 适合问“某个主题、某个实体附近有什么信息”
- `global` 适合问“整篇公报讲了什么主线、全局有哪些重点”
- `drift` 适合先找主题再扩展关系链，兼顾全局与局部
- `basic` 适合在高阶模式失败或对速度更敏感时快速响应

**方法优势：**

- 质量与速度之间可以分层折中
- 高阶检索失败时不会立刻全盘报错
- 适合真实办公中的不同问题粒度

### 5.1.3 文本语料合成与清洗方法

**当前方案：**

- 使用模块二工件做语义重组
- 对噪声结构、artifact 编号、乱码、无意义表壳行做显式过滤
- 将结构化结果转写为更适合 GraphRAG 的描述性文本

**为什么这样选：**

- 原始文档文本不一定是最佳入图材料
- 模块二已经完成的结构化抽取、摘要、trace 结果如果不被利用，会造成信息浪费
- GraphRAG 更依赖高质量的、可叙述的文本输入，而非脏乱的原始壳层文本

**效果优势：**

- 降低噪声实体比例
- 提升社区报告可读性
- 提高图谱主题聚类质量

### 5.1.4 风险规则与可解释方法

**当前方案：**

- 规则引擎：deterministic rules
- 解释：Explain
- 模拟：Simulate

**为什么这样选：**

- 在正式业务场景中，很多风险规则并不适合完全交给模型自由判断
- 低置信度、质量退化、字段异常等问题更适合显式规则定义
- Explain / Simulate 能把规则结果转化为“可说明、可复核、可推演”的输出

**效果优势：**

- 可审计
- 可复核
- 可维护
- 更适合落地业务治理

### 5.1.5 图谱前端渲染与交互方法

**当前方案：**

- 图谱画布组件：`Module4GraphCanvasG6`
- 渲染模型构建：
  - `buildGraphRAGOverviewModel`
  - `buildGraphRAGCommunityFocusModel`
  - `buildGraphRAGEntityDrilldownModel`

**为什么这样选：**

- 真实图谱节点多、边多，如果不做标签抑制、视图模式切换与后布局优化，页面会迅速变成“不可读散点图”
- G6 类图组件更适合复杂节点边可视化与交互控制
- overview / community-focus / entity-drilldown 三种视图模式，能支持从宏观到局部的逐层阅读

**效果优势：**

- 适合汇报态展示
- 适合主题聚焦
- 适合复杂图谱的画布级浏览

## 8. 当前状态与风险提示

### 8.1 已验证稳定部分

- 模块四后端服务已启动且健康检查通过
- PostgreSQL 连接正常
- GraphRAG runtime readiness 正常
- 当前存在多份 ready 图谱
- 网页端知识图谱工作台可真实渲染图谱
- 文件切换、视图控制、关系筛选等前端功能可用
- 规则列表接口可正常返回

### 8.2 当前主要限制

#### 限制一：GraphRAG 查询链路仍有旧工作空间路径残留

当前 ready 图谱版本中的：

- `workspace_dir`
- `output_dir`
- `artifacts_dir`

仍然记录为旧路径：

- `backend/module4/workspaces/...`

而当前项目中的模块四源码与运行目录已经迁移到：

- `backend/app/modules/module4/...`

因此，图谱浏览虽然还能基于存储快照工作，但 GraphRAG query 需要读取 artifacts 时，会出现“路径存在性失败”。

#### 限制二：图谱画布当前仍然偏密

从真实截图看，当前图谱总览态已经可渲染，但标签密度较高，宏观可视化效果仍有优化空间，尤其在：

- 标签重叠控制
- 社区聚焦默认视图
- 初始相机视角
- 默认关系过滤策略

方面还可以继续优化。

#### 限制三：手机端尚未形成模块四独立工作台

当前手机端前端仍以首页入口页为主，尚未像网页端一样形成完整的知识图谱工作台体验。

#### 限制四：依赖版本文档口径需要后续统一

当前 `README.md / requirements.txt` 中对 GraphRAG 版本的说明与实际健康检查返回的运行时版本口径存在差异，后续建议统一为“以当前生产运行环境健康检查结果为准”。

### 8.3 建议的答辩口径

如果需要面对评审或汇报场景，建议这样表述：

- 模块四的主体能力已经成形，能够完成“文档结果入图、图谱可视化、文件级图谱管理、规则与证据联动、Explain / Simulate 分析”等核心闭环。
- 当前最主要的问题不是模块四没有能力，而是“后端目录重构后，历史 ready 图谱的 artifacts 路径记录还未完全收口”，导致 GraphRAG query 在部分历史图谱上会报路径错误。
- 这属于“迁移收口型问题”，不是“体系设计失败型问题”。

## 9. 综合评价

综合来看，模块四已经具备较强的知识图谱产品雏形和技术深度，其价值并不只是“把文档变成一张图”，而是完成了以下层面的升级：

- 从文档结果到知识结构的升级
- 从关键词检索到社区级语义检索的升级
- 从图谱展示到证据-规则-告警闭环的升级
- 从图谱问答到 Explain / Simulate 分析的升级
- 从单次脚本构建到长期服务治理的升级

如果用一句更项目化的话来总结模块四：

> **模块四不是一个附属的可视化页面，而是整个系统中承接“结构化理解 -> 知识组织 -> 风险智能 -> 研判支持”的关键智能中枢。**

当前如果把“历史路径残留导致的 GraphRAG 查询失败”这一迁移问题收口完成，模块四会从“已具备完整能力框架的图谱工作台”进一步迈向“真正可长期稳定交付的图谱智能模块”。
