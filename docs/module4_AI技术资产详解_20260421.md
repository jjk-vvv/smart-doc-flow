# 模块四 AI 技术资产详解

## 1. 编写目的

本文档用于系统梳理模块四中与人工智能能力直接相关的技术资产，重点覆盖以下三类内容：

1. GraphRAG Prompt 包
2. 从模块二产物再生出来的图谱语料
3. 模块二评测题库与模块四自动评测脚本之间的衔接关系

本文的目标不是单纯罗列文件，而是从资产边界、运行机制、工程价值和维护方法四个层面，说明模块四的 AI 资产体系是如何被组织起来的。

## 2. 总体结论

模块四的 AI 资产体系不是围绕“单次图谱构建”组织的，而是围绕“Prompt 资产可控、语料来源可追踪、workspace 可复现、查询与评测可回归”组织的。其整体结构可以概括为三层：

1. GraphRAG Prompt 资产层，负责定义图谱抽取、摘要、社区报告、局部搜索、全局搜索和问题生成等行为。
2. 图谱语料再生层，负责把模块二产生的多类文档工件再加工成适合 GraphRAG ingestion 的文本语料。
3. 评测与验证层，负责用自动评测脚本验证非 PDF 数据集在图谱构建后的结构质量，并与模块二人工评测体系形成互补。

从方案层面看，模块四最核心的设计思想是：不是直接把原始文档一股脑扔给 GraphRAG，而是先利用模块二的文档解析结果做二次结构化，再把更“检索友好、图谱友好、事实友好”的文本投喂给 GraphRAG。

### 3.3 Prompt 包的分层结构

从职责角度看，这 13 份 Prompt 可以划分为四组：

#### 3.3.1 图谱构建组

包括：

1. 图谱实体关系抽取系统提示词（`extract_graph`）
2. 实体描述归并系统提示词（`summarize_descriptions`）
3. 实体声明抽取系统提示词（`extract_claims`）

这一组负责把输入文本转化为图谱可消费的结构信息，是 indexing 阶段最核心的 Prompt 资产。

#### 3.3.2 社区报告组

包括：

1. 关系视角社区报告系统提示词（`community_report_graph`）
2. 文本叙事社区报告系统提示词（`community_report_text`）

这一组负责把社区级别的图谱与事实关系再整理成面向分析者和决策者的报告。

#### 3.3.3 查询搜索组

包括：

1. 局部图谱问答系统提示词（`local_search_system_prompt`）
2. 全局搜索映射阶段系统提示词（`global_search_map_system_prompt`）
3. 全局搜索归并阶段系统提示词（`global_search_reduce_system_prompt`）
4. 全局搜索知识补充系统提示词（`global_search_knowledge_system_prompt`）
5. 漂移搜索系统提示词（`drift_search_system_prompt`）
6. 漂移搜索归并系统提示词（`drift_reduce_prompt`）
7. 基础搜索系统提示词（`basic_search_system_prompt`）

这一组负责问答运行期的不同查询模式。

#### 3.3.4 问题生成组

包括：

1. 问题候选生成系统提示词（`question_gen_system_prompt`）

这一组用于做问题建议、问题扩展或分析入口构建。

### 3.4 `prompts.py` 的资产化价值

`backend/app/modules/module4/services/graphrag/prompts.py` 并不只是把文件路径映射出来，它实际上完成了三件事：

1. 用 `PROMPT_ASSETS` 把每份 Prompt 定义成显式资产对象，包含 `key / filename / description`。
2. 用 `PROMPT_KEY_TO_ENV` 将 Prompt 和环境变量覆写机制绑定。
3. 通过 `PromptRegistry` 提供 `prompt_path`、`prompt_text`、`manifest`、`materialize` 四类能力。

这意味着模块四的 Prompt 包已经具备正式“资产注册表”的形态，而不是若干离散文本文件。

### 3.5 Prompt 的覆写与路径解析机制

模块四的 Prompt 不是写死路径的。其覆盖链路大致如下：

1. `settings.py` 从环境变量读取 Prompt 文件名或 Prompt 根目录。
2. `GraphRAGRuntimeSettings.prompt_overrides()` 输出逻辑级别的 Prompt 覆写映射。
3. `PromptRegistry.prompt_path()` 根据 `asset_root + overrides + env` 解析真实文件路径。
4. `workspace.py` 在构建 workspace 时调用 `PromptRegistry.materialize()`，把当前有效 Prompt 复制进当前 workspace 的 `prompts/` 目录。
5. `workspace.py` 再将这些 Prompt 引用写入 `.env` 与 `settings.yaml`。

这套机制的核心意义是：

1. Prompt 可以被版本化替换。
2. 每个 workspace 都能保存一份执行时快照。
3. Prompt 改动后，运行时可以明确知道实际使用了哪份资产。

### 3.6 查询阶段对 Prompt 的强制校准

`backend/app/modules/module4/services/graphrag/query_service.py` 中的 `_apply_query_prompt_paths()` 很关键。它显式指出：

1. 历史 workspace 中可能存在陈旧 Prompt 快照。
2. 查询阶段应尽量使用模块四 canonical prompt，而不是盲目沿用旧 workspace 快照。

因此，模块四不是简单“用工作区里的 Prompt 就算了”，而是在查询阶段加了一层最新 Prompt 覆盖机制，以降低历史 Prompt 漂移带来的风险。

### 3.7 Prompt 健康检查机制

`backend/app/modules/module4/services/graphrag/indexer.py` 中的 `_missing_prompt_assets()` 与 `probe()` 会在运行前检查：

1. Prompt 根目录是否存在。
2. 每个已注册 Prompt 文件是否存在。
3. Prompt 缺失是否会影响 runtime readiness。

这意味着模块四把 Prompt 缺失视为正式的运行时依赖问题，而不是等到索引失败后再模糊报错。

### 3.8 模块四 Prompt 资产的工程价值

模块四 Prompt 包的真正价值体现在：

1. 它把 GraphRAG 核心行为全都 Prompt 化、资产化、注册化。
2. 它支持 workspace 级快照，便于复现。
3. 它支持 query 运行期的 canonical 覆盖，便于修正旧快照漂移。
4. 它支持健康探针检查，便于提前发现运行风险。

### 3.9 模块四提示词的构建逻辑

模块四的提示词构建逻辑，与模块二明显不同。它不是在 Python 中持续拼装一大段动态 Prompt，而是采用“Prompt 资产注册 + 路径解析 + Workspace 物化 + GraphRAG 配置绑定 + 查询期校正”的构建方式。

#### 3.9.1 先把 Prompt 当成正式资产注册，而不是散落的模板文件

`backend/app/modules/module4/services/graphrag/prompts.py` 中的 `PROMPT_ASSETS` 会先把 13 份 Prompt 资产全部登记在册，每一项都至少包含：

1. `key`
2. `filename`
3. `description`

同时，`PROMPT_KEY_TO_ENV` 会把每个 Prompt 和环境变量覆写键一一绑定。这意味着模块四提示词构建的第一步，不是“生成文本”，而是“确定当前系统有哪些 Prompt 资产、每个资产的逻辑身份是什么”。

#### 3.9.2 `settings.py` 负责把运行时配置转化为 Prompt 选择结果

`backend/app/modules/module4/services/graphrag/settings.py` 会读取：

1. Prompt 根目录
2. 各 Prompt 文件名
3. 各 Prompt 的环境变量覆写项

再通过 `GraphRAGRuntimeSettings.prompt_overrides()` 输出当前运行时的 Prompt 覆写映射。也就是说，模块四提示词构建的第二步不是直接读文件，而是先根据当前环境和运行设置，决定“本次到底应该选用哪一份 Prompt 文件”。

#### 3.9.3 `PromptRegistry` 负责把逻辑 Prompt 解析成真实文件路径

`PromptRegistry.prompt_path()` 的解析顺序大致是：

1. 先看显式 override
2. 再看环境变量 override
3. 最后退回默认 Prompt 根目录下的默认文件

因此，模块四提示词构建的第三步是“把逻辑 Prompt 身份解析成当前实际生效的物理文件路径”。这一步是后续 workspace 构建和查询阶段统一使用 Prompt 的基础。

#### 3.9.4 Workspace 构建阶段会把 Prompt 物化到当前工作区

在 `backend/app/modules/module4/services/graphrag/workspace.py` 中，`GraphRAGWorkspaceBuilder.prepare_workspace()` 会调用 `PromptRegistry.materialize()`，把当前生效的 Prompt 文件复制到当前 workspace 的 `prompts/` 目录中。

随后，系统还会继续生成：

1. `.env`
2. `settings.yaml`
3. `workspace_manifest.json`

这意味着模块四提示词构建的第四步，不是只在内存里记住 Prompt 路径，而是把它们正式固化为当前 workspace 的可复现快照。

#### 3.9.5 `settings.yaml` 才是 Prompt 真正进入 GraphRAG 运行时的入口

在 `render_settings_yaml()` 中，系统会把各 Prompt 路径写入 GraphRAG 配置。例如：

1. `extract_graph.prompt`
2. `summarize_descriptions.prompt`
3. `extract_claims.prompt`
4. `community_reports.graph_prompt`
5. `community_reports.text_prompt`
6. `local_search.prompt`
7. `global_search.map_prompt`
8. `global_search.reduce_prompt`
9. `global_search.knowledge_prompt`
10. `drift_search.prompt`
11. `drift_search.reduce_prompt`
12. `basic_search.prompt`

因此，模块四提示词构建的第五步，才是把 Prompt 文件路径正式绑定到 GraphRAG 的索引阶段和查询阶段执行配置中。

#### 3.9.6 查询阶段会强制校正到最新 canonical Prompt

`backend/app/modules/module4/services/graphrag/query_service.py` 中的 `_apply_query_prompt_paths()` 会在查询执行前，再把查询相关 Prompt 路径重新校正到模块四当前的 canonical Prompt 资产目录。

这样做的目的非常明确：

1. 防止旧 workspace 中残留过时 Prompt 快照
2. 保证查询行为尽量跟随当前最新 Prompt 资产
3. 降低历史 Prompt 漂移对问答结果的影响

这说明模块四提示词构建并不是“一次构建，到处沿用”，而是在查询期还有一层动态修正。

#### 3.9.7 Prompt 模板内部的占位符由 GraphRAG 运行时填充

模块四 Prompt 文件大多是静态模板，但模板内会保留少量占位参数，例如：

1. `{entity_types}`
2. `{input_text}`
3. `{context_data}`
4. `{response_type}`
5. `{max_length}`
6. `{report_data}`
7. `{question_count}`

因此，模块四提示词构建的第六步，不是在 Python 里手工拼完整 Prompt 文本，而是先选定模板，再由 GraphRAG 在具体运行阶段把这些占位内容填进去。

#### 3.9.8 真正喂给 Prompt 的内容来自模块二产物重组后的语料

模块四提示词的“文本模板”虽然主要存放在 `assets/prompts/` 目录中，但它们吃进去的 `input_text`、`context_data` 并不是原始文档裸文本，而是由 `backend/app/modules/module4/services/ingestion/text_corpus.py` 从模块二产物中重组出来的图谱语料。

这部分语料通常会综合：

1. 原始 `source_texts`
2. 模块二 markdown 工件
3. 助手 payload 工件
4. xlsx workbook / sheet 行数据工件
5. 字段抽取结果工件
6. trace hits 与 locator 摘要

所以，模块四提示词构建逻辑必须拆成两半理解：

1. Prompt 文件本身如何被注册、选择、绑定和校正
2. Prompt 真正消费的语料是如何从模块二处理结果中再生出来的

只有这两部分同时成立，模块四的 GraphRAG 提示词链路才是完整的。

## 4. 模块四从模块二产物再生出来的图谱语料

### 4.1 资产定位

模块四最有技术含量的部分之一，不是 Prompt，而是图谱语料的再生逻辑。核心文件位于：

`backend/app/modules/module4/services/ingestion/text_corpus.py`

这份代码的作用不是简单读取原文，而是从模块二已经产出的多类结构化、中间态和补充工件中，重新拼装出更适合 GraphRAG ingestion 的文本。

### 4.2 为什么要做“再生语料”

如果直接使用原始文档文本做图谱抽取，会遇到几个典型问题：

1. 原始文档中混有大量格式壳层、分页噪声、表格壳层和无效标记。
2. 有价值的字段抽取结果、表格归一化结果、工作簿清单和助手整理结果没有被利用。
3. 图谱关心的是“可复用事实文本”，而不是文档展示层的原始布局细节。

因此，模块四不是直接依赖“原文”，而是依赖“模块二处理后的事实富集文本”。

### 4.3 语料来源层级

根据 `text_corpus.py` 的实现，模块四会从以下来源重组语料：

#### 4.3.1 模块二 artifact 根目录

代码会通过 `_module2_artifact_root()` 和 `_resolve_artifact_path()` 定位模块二 artifact 目录，默认指向：

`runtime-data/module2/artifacts`

这使模块四能直接消费模块二运行过程中沉淀下来的结构化工件。

#### 4.3.2 原始 `source_texts`

`_append_source_text_entries()` 会读取文档中已经整理好的 `source_texts`，并区分：

1. 主证据文本
2. trace 类或 locator 类二级文本
3. 对应 `.txt`、`.md` artifact 的补充文本

#### 4.3.3 模块二 markdown 产物

`_append_module2_artifact_texts()` 会优先读取：

1. `assistant1_source_markdown_artifact_path`
2. `markdown_artifact_path`

读取后还会做 `<ref>` 标签剥离，保留更干净的文本内容。

#### 4.3.4 assistant payload 产物

`assistant_payload_artifact_path` 对应的 JSON 也会被读取，并从中提取文本片段。这意味着模块四不仅消费原始解析文本，也消费助手整理后的中间结构。

#### 4.3.5 xlsx 工作簿与 sheet rows 产物

模块四专门处理了两类 Excel 工件：

1. `xlsx_workbook_manifest`
2. `xlsx_sheet_rows`

这说明模块四在 ingest 图谱时，不是把 Excel 当普通二进制附件，而是尽量把 workbook 清单、sheet 行数据转成可被图谱利用的文本事实。

#### 4.3.6 字段结果产物

`_append_field_results_artifact()` 会读取 `field_results_artifact_path`，把字段抽取结果转换成文本片段，例如“字段抽取结果：某字段 = 某值”这一类事实表达。

#### 4.3.7 文档结果与 trace 命中

在 `_compose_document_text()` 中，模块四还会继续补充：

1. `result` 字段中的结构化结果
2. `trace_hits` 中的 snippet
3. locator 的 `summary / caption / title`

这使最终语料同时具备：

1. 原始语义
2. 字段事实
3. 溯源摘要
4. 表格/图表定位信息

### 4.4 语料清洗机制

`text_corpus.py` 不只是拼文本，更重要的是清洗噪声。它至少做了以下处理：

1. 剥离 `<ref>` 标签。
2. 统一空白字符。
3. 识别并过滤 mojibake。
4. 过滤 artifact id、xlsx ref id、markdown 表格分隔线等展示壳层。
5. 过滤 `artifact_path`、`artifact_url`、`bbox`、`ref_id`、`page` 一类技术性展示字段。
6. 识别空白值、占位值、`N/A`、`null`、`-` 一类无效值。
7. 通过 `seen` 集合做去重。

从图谱质量角度看，这套清洗逻辑决定了模块四不会把大量展示残渣、乱码和技术壳层当成事实送进图谱。

### 4.5 语料分桶机制

`_compose_document_text()` 中把片段分成三类：

1. `title_fragments`
2. `primary_fragments`
3. `secondary_fragments`

最后再按“标题 -> 主文本 -> 次级文本”的顺序拼接。这种做法有两个好处：

1. 先给图谱一个稳定的标题与主语义框架。
2. 再补充字段、trace、定位类辅助信息，而不是让所有片段平权混排。

### 4.6 再生语料的最终输出形态

模块四的 workspace builder 会把标准化后的文本封装为 `WorkspaceSourceFile`，再写入当前 workspace 的 `input/` 目录，形成标准 `.txt` 输入文件。与此同时，还会生成：

1. `.env`
2. `settings.yaml`
3. `workspace_manifest.json`

这样一来，图谱输入不是黑盒，而是具备：

1. 输入文本文件
2. Prompt 快照
3. 运行参数
4. 文件级 manifest

的完整可复现工作区。

### 4.7 再生语料机制的核心价值

这套“从模块二产物再生图谱语料”的机制，带来的价值非常明确：

1. 图谱 ingest 不再只依赖原始原文，而是能消费模块二已经识别出来的结构事实。
2. Excel、字段抽取、助手整理结果都能进入图谱，而不是浪费掉。
3. 图谱语料质量更高，更接近“事实集合”，而不是“视觉残片集合”。
4. 文档处理链和知识图谱链形成了真正的数据闭环。

## 5. 模块二评测题库与模块四自动评测脚本的衔接

### 5.1 评测体系的互补关系

模块二和模块四虽然属于不同能力层，但在评测上形成了互补关系：

1. 模块二评测题库偏“人工视角、回答质量、用户问题完成度”。
2. 模块四自动评测脚本偏“结构视角、图谱生成质量、文件对齐质量”。

前者回答“这个助手好不好用”，后者回答“这条图谱链路跑出来的结构是否像样”。

### 5.2 模块二评测题库的衔接价值

模块二评测题库位于：

`docs/superpowers/specs/2026-04-10-module2-assistant-eval-question-bank.md`

它与模块四的关系在于：

1. 模块二题库定义了什么叫 grounded、什么叫不胡编、什么叫可追溯、什么叫缺失处理正确。
2. 这些标准也直接影响模块四的上游事实质量。
3. 如果模块二在字段抽取、定位、摘要或证据表达上出问题，模块四拿到的图谱语料质量也会下降。

因此，这份题库虽然属于模块二，但对模块四的图谱质量同样具有上游约束意义。

### 5.3 模块四自动评测脚本位置

模块四自动评测脚本位于：

`backend/app/modules/module4/tools/nonpdf_alignment_eval.py`

它的定位非常明确：对 `datasets` 目录下的非 PDF 文件做文件级 GraphRAG 对齐评估。

### 5.4 自动评测脚本的输入覆盖范围

该脚本支持的文件后缀主要包括：

1. 文本类：`.txt`、`.md`、`.markdown`、`.csv`、`.tsv`、`.json`、`.yaml`、`.yml`
2. Office 类：`.docx`、`.xlsx`

并显式排除了 `.pdf`。

这说明它的目标不是做 PDF OCR 评测，而是验证模块四对非 PDF 数据集的 ingest 对齐质量。

### 5.5 自动评测脚本的执行过程

`nonpdf_alignment_eval.py` 的核心执行流程大致如下：

1. 遍历数据集根目录中的非 PDF 文件。
2. 按文件类型提取纯文本。
3. 对 docx 解析 `word/document.xml`，提取文本。
4. 对 xlsx 解析 `sharedStrings` 与 `worksheets/sheet*.xml`，还原行文本。
5. 将文本裁切到安全长度。
6. 构造 `IngestRequest`，以 `source="module2"`、`graph_mode="hybrid"` 的方式进入模块四 ingest。
7. 读取生成后的 graph file。
8. 加载 artifact graph snapshot。
9. 统计节点数、边数、节点类型分布、关系类型分布，以及是否存在替换字符异常。
10. 汇总生成 JSON 报告。

这说明模块四的自动评测不是做简单文本检查，而是实际走了一遍图谱 ingest 主链路。

### 5.6 自动评测输出指标

脚本的最终汇总指标包括：

1. `files_total`
2. `files_ok`
3. `files_skipped`
4. `replacement_char_files`
5. `node_types_total`
6. `relation_types_total`
7. `expected_node_types`
8. `expected_relations`

单文件层面还会输出：

1. 文件相对路径
2. 后缀
3. 状态
4. 跳过原因
5. 文本字符数
6. 节点数
7. 边数
8. 节点类型分布
9. 关系类型分布
10. 是否出现替换字符

这套指标足以用来评估：

1. 某种文件格式是否能稳定进入图谱。
2. 图谱结果是否为空。
3. 结构类型是否基本合理。
4. 是否存在编码污染问题。

### 5.7 模块二题库与模块四自动评测脚本的分工

两者分工可以概括为：

| 资产 | 核心视角 | 主要问题 |
| --- | --- | --- |
| 模块二评测题库 | 用户视角、助手视角 | 回答是否 grounded、是否会澄清、是否有用、是否可信 |
| 模块四自动评测脚本 | 结构视角、图谱视角 | 文件能否被 ingest、图谱是否生成、节点关系是否合理、编码是否异常 |

这意味着：

1. 模块二题库更适合验证“问答质量”。
2. 模块四脚本更适合验证“图谱链路质量”。
3. 两者合起来，才能真正覆盖从文档处理到知识图谱落地的全链路质量。

## 6. 模块四 AI 技术资产的整体评价

模块四当前的 AI 技术资产体系具备以下特征：

1. GraphRAG Prompt 已经形成注册表、路径解析、workspace materialize、查询期覆盖和健康检查的完整资产管理链。
2. 图谱语料并非直接吃原文，而是复用了模块二解析后的高价值工件，具备明显的二次结构化优势。
3. 自动评测脚本已经能够基于真实文件集验证非 PDF 数据的图谱对齐情况。
4. 模块二评测题库与模块四自动评测脚本构成了“人工质量验证 + 自动结构验证”的双层评测体系。

如果从方案语言做一句话总结，可以表述为：

模块四已经形成了“Prompt 资产层 + 语料再生层 + workspace 复现层 + 自动评测层”四层协同的 GraphRAG 技术资产体系。

## 7. 后续治理建议

为进一步提升模块四 AI 资产的可维护性与可审计性，建议后续继续推进以下工作：

1. 为 13 份 Prompt 增加资产说明索引，避免后续维护者只知道文件名，不知道各自负责哪一段工作流。
2. 为 `text_corpus.py` 增加输入来源统计与命中统计，明确每次图谱语料有多少内容来自模块二 markdown、field results、xlsx rows 和 trace hits。
3. 将 `nonpdf_alignment_eval.py` 的结果接入更稳定的报告归档机制，形成可对比的回归报告。
4. 将模块二人工题库中的高价值问题与模块四图谱结果做联动验证，形成“同一文档在问答层和图谱层的一致性评测”。
5. 为 workspace manifest 增加 Prompt 版本摘要与语料来源摘要，提升复现与审计能力。
