## 3. 创新性解决方案
结合代码实现、系统运行方式与外部资料依据，模块二的创新性解决方案可概括为以下九点：

（1）使用了 MinerU + Gemini Vision 协同的视觉优先解析策略，在 PDF 与复杂 Office 文档处理中，由 MinerU 先完成版面结构恢复、页面对象切分、表格区域识别、图表候选定位和基础内容重建，再由 Gemini Vision 对关键 ROI、表格块、图表块和复杂视觉片段进行语义理解、字段补充和证据增强，改变了传统系统“先 OCR 出文本、再做字段抽取”的单一路径，解决了扫描件、图文混排文档、复杂排版报告中“能读到文字但无法稳定理解结构、能定位区域但无法理解含义”的问题，从而在保证抽取精度的同时提升了视觉理解深度、字段可解释性和原文可溯源能力。

（2）使用了规则、启发式与大模型协同的自动 Schema 推断策略，在用户未预先给定字段模板时，系统能够根据文档标题、表头、键值结构、图表语义和领域词汇自动判断“当前文档最值得抽取哪些字段、这些字段应属于什么类型”，解决了开放式文档场景下“抽取前并不知道该定义什么字段”的问题，从而提高了系统面对不同文档类型时的泛化能力与启动效率。

（3）使用了图式化、分阶段的字段抽取策略，将抽取过程显式拆分为 `table_profile -> table_extract -> text_rule_extract -> extract -> validate -> resolve_dependencies` 多个节点，而不是把全部字段一次性交给大模型直接生成，解决了一次性输出容易出现的空值、错位、字段类型漂移和依赖字段遗漏等问题，从而在复杂表格和长文档场景下显著提升了结构化抽取的稳定性与可控性。

（4）使用了 Word 原生结构解析与 Office 转 PDF 视觉解析结合的混合处理策略，在保留 DOCX 原生文本和结构信息的同时，引入图表 XML 恢复、媒体探测、Office 预览转换与视觉优先补充链路，解决了传统 Word 解析中“纯文本链路可读但图表和复杂版式信息容易丢失”的问题，从而兼顾了处理速度、解析完整性和复杂文档质量。

（5）使用了面向工作簿的 XLSX 结构理解策略，将 Excel 文件按 workbook、sheet、row、cell 进行结构化建模，并生成 workbook manifest、sheet rows artifact 和前端局部投影数据，而不是将整个表格粗暴转成纯文本再喂给模型，解决了大表格场景中字段缺失、上下文断裂、整表 prompt 过载和前端无法高效预览的问题，从而为字段抽取、局部定位和后续数据可视化表达提供了稳定的数据底座。

（6）使用了字段级原文溯源与证据回链策略，为每个抽取结果保留 `ref_id`、`page`、`bbox`、`artifact_url`、`trace_hits` 等证据索引信息，解决了传统抽取系统“只有结果、没有证据、人工无法复核”的问题，从而使模块二不仅能够给出结构化答案，还能够解释答案来自哪一页、哪一块、哪一张表、哪一处原文，对政务、科研、企业归档等高可信场景更具实际价值。

（7）使用了基于 Function Calling 的 grounded assistant 设计策略，将文档摄入、知识单元构建、向量检索、结果重排、Web Search、数据库结构探查、自然语言转 SQL、SQL 执行和流式回答统一收敛到 Assistant_1 中，并通过模型原生函数调用能力让大模型先选择工具、组织参数、触发执行，再将工具返回结果以 `function_call_output` 的形式回灌给模型生成最终答案，改变了传统文档助手只能做泛化聊天、即使接了工具也常常只是外围脚本拼接的模式，解决了“文档解析结果难以继续被高质量使用、工具能力无法真正内化进回答链路”的问题，从而把模块二从单纯的抽取系统提升为可持续交互、可调用外部能力、可执行复杂任务的文档智能工作台。

（8）使用了模块二到模块四的 Outbox 异步同步策略，将主抽取链路与下游知识图谱链路进行解耦处理，通过 outbox 持久化、异步投递、失败重试、延时重放与状态跟踪机制，解决了下游模块波动时主抽取流程被整体阻塞的问题，从而提高了多模块协同架构下的系统稳定性、可恢复性与工程扩展能力。

（9）使用了质量门控、动态预算与运行时恢复结合的工程策略，在长文档、多文件并发、Office 转换、高成本视觉解析等场景下引入动态超时预算、缓存恢复、singleflight、防重复转换、质量快照与结果过滤等机制，解决了复杂文档处理中常见的性能抖动、重复计算、低质量结果混入和异常链路难恢复的问题，从而保证模块二在真实业务环境中不仅“能跑”，而且“能稳定跑、能持续交付”。

## 4. 功能特色与办公场景优势
下面从真实办公场景切入，结合市面常见文档编辑软件、纯 OCR 软件、传统 IDP 平台和单点 AI 助手的能力边界，模块二的功能特色可概括为以下八点：

（1）在政府统计公报、行业分析报告、年度发展白皮书等长文档场景中，模块二的特色不是“把文档打开并展示出来”，而是能够直接抽取人口、GDP、产业结构、财政收入、投资增速、居民收入等关键指标，并同步保留字段来源页码、原文片段和证据定位信息。相较于 Microsoft 365、Adobe Acrobat、WPS 这类以阅读、编辑、批注和摘要为主的软件，模块二更适合承担“从长报告中快速沉淀关键事实”的工作，尤其适合政务研判、产业研究、课题分析和资料归档等需要结构化结论的场景。

（2）在企业合同、制度文件、通知公告、会议纪要、申报材料等内部办公文档场景中，模块二的特色在于能够把文档中的主体名称、签署日期、金额条款、责任部门、时限要求、关键事项等内容抽取成结构化字段，而不是只停留在全文检索或人工阅读层面。相较于传统文档管理系统只能“存文档、搜文档、看文档”，模块二更适合做“从文档中提取管理要素”，因此在合同归档、制度追踪、通知闭环管理和审计资料整理中更具实际办公价值。

（3）在扫描 PDF、拍照件、图文混排报告、带图表和复杂版式的研究资料场景中，模块二的特色在于采用 MinerU + Gemini Vision 协同视觉链路，不仅能识别文字，还能识别页面中的表格区域、图表对象、图像证据和版面层级，并将最终字段结果回落到具体证据块。相较于纯 OCR 软件只擅长“把图片转成文本”，模块二更适合处理“能看到内容但难以稳定理解结构”的复杂文档，因此特别适合扫描档案、研究报告、统计图册、图文型公文和复杂排版 PDF 的高质量解析。

（4）在环境监测台账、岗位职位表、经营报表、统计明细表、清单台账等 Excel 大表场景中，模块二的特色在于以工作簿理解为核心，将 XLSX 按 workbook、sheet、row、cell 做结构化处理，并生成可供前端预览、字段抽取和局部投影的数据产物。相较于传统 IDP 系统对 Excel 常常只做模板匹配或整表转文本，模块二更适合处理字段多、行数大、结构变化频繁的工作表，因此在监测数据治理、业务台账分析、批量信息核对和结构化数据预处理等场景下更有优势。

（5）在半结构化文档场景中，模块二的特色在于不强依赖固定模板，而是通过自动 Schema 推断、规则与启发式筛选、图式抽取和字段规范化机制，自动判断“这份文档应该抽什么”。这使得系统不仅能处理固定模板的表单型资料，也能处理统计公报、行业分析、项目汇报、监测日报、说明材料等开放式内容。相较于传统 IDP 平台更依赖预配置模板，模块二更适合面对真实办公中格式不完全统一、但又需要稳定抽取结果的半结构化文档场景。

（6）在需要人工复核、专家审查、业务追责和结果佐证的高可信场景中，模块二的特色在于提供字段级原文溯源能力。每个字段不仅有值和置信度，还能对应到 `ref_id`、`page`、`bbox`、`trace_hits`、artifact 图像和原文摘要，从而支持“结果可复查、证据可回看、结论可解释”的工作方式。相较于很多抽取系统只返回结果、不返回证据，模块二更适合政务报送、科研材料核验、企业风控、审计检查和管理层决策支持等对可信度要求更高的场景。

（7）在“文档解析后还要继续问答、分析和决策”的场景中，模块二的特色在于内置 Assistant_1，并采用基于 function calling 的 grounded assistant 机制，把知识库检索、Web 搜索、数据库结构探查、自然语言转 SQL、SQL 执行等工具真正接入回答链路。相较于很多单点 AI 助手只能做泛化对话、不能稳定利用当前文档和外部工具，模块二更适合做“先解析文档，再围绕文档继续提问、分析、追问、生成结论”的深度办公协同，因此在材料研判、信息核查、方案问答、数据追问和辅助分析中更具实用性。

（8）在“文档不是一次性消费，而是后续还要沉淀为知识资产”的场景中，模块二的特色在于抽取结果不会停留在前端展示层，而是会继续沉淀为 trace、artifact、assistant payload，并通过 outbox 异步同步到模块四，进入知识图谱和下游知识网络。相较于普通文档软件和普通 AI 助手“处理完即结束”的模式，模块二更适合承担“文档即数据资产、文档即知识资产”的中台角色，因此在知识沉淀、组织记忆建设、跨文档关联分析和后续图谱检索等场景下拥有更长的价值链条。

## 5. 详细功能设计

## 5.1 模型与方法选择

### 5.1.1 抽取主模型

当前模块二 `.env.example` 中的抽取主模型配置为：

- `MODULE2_LLM_PROVIDER=gemini_native`
- `MODULE2_LLM_MODEL=gemini-3.1-pro-preview`
- `MODULE2_GEMINI_VISION_MODEL=gemini-3.1-pro-preview`

为什么选择这一路线：

- 需要同时覆盖文本抽取与视觉增强。
- 需要较长上下文容纳字段候选、表格上下文、trace refs。
- 需要 JSON 化输出与多轮修复能力。

相较替代方案：

| 方案 | 优点 | 局限 | 模块二为何不单独采用 |
| --- | --- | --- | --- |
| 纯规则 / 正则 | 快、确定性强 | 面对复杂文档泛化差 | 只能做辅助，不能单独扛住开放文档抽取 |
| 纯 OCR + 正则 | 对扫描件有基础可用性 | 表格/图表理解弱 | 无法支撑复杂文档与原文证据回链 |
| 一次性 LLM 抽取 | 开发快 | 结果不稳、难验证、难回溯 | 模块二转向图式抽取与显式验证 |
| 小模型抽取 | 成本低 | 在复杂文档与长上下文下易失真 | 当前质量目标更偏向复杂办公文档 |

### 5.1.2 视觉与版面方法

模块二的视觉链路采用：

- MinerU / layout-aware PDF parsing
- ROI 裁剪
- Gemini 视觉理解
- 表格 / 图表 / 图片对象归一化

为什么这样选：

- 单纯 OCR 拿不到稳定布局结构。
- 单纯原生 PDF 文本在图表、截图、扫描页上不够用。
- 视觉对象拆解后更容易做 trace 回链与前端展示。

### 5.1.3 XLSX 方法

模块二对 XLSX 走的是“结构化工作簿解析”而非“截图识别”。

为什么这样选：

- Excel 的核心价值往往在“行列关系”和“数据分布”，不是纯文本句子。
- workbook / sheet / row / cell 的结构更适合字段抽取和可视化。
- 对大表可以只展示局部投影，避免前端和模型双重超载。

### 5.1.4 Assistant_1 的模型与检索方法

当前 Assistant_1 配置显示：

- Embedding 默认模型：`gemini-embedding-001`
- Document task type：`RETRIEVAL_DOCUMENT`
- Query task type：`RETRIEVAL_QUERY`
- Chat 模型代码默认回退：`gpt-5-mini`
- `.env.example` 样例：`gpt-4.1-mini`
- Chat endpoint style：`openai_responses` / `openai_chat_completions`
- Assistant 内部支持基于 function calling 的工具调用闭环

为什么这样选：

- 文档检索需要专门 embedding 模型，而不是把聊天模型直接拿来做向量。
- Chat 层与 Embedding 层解耦，更利于成本、延迟和质量分别调优。
- Assistant_1 需要 grounded QA，因此“检索 + function calling + 工具执行 + 流式输出”比单模型直答更合理。
- 对于数据库分析、知识库检索、Web 搜索这类任务，function calling 能让模型先决定调用哪个工具、再基于工具结果继续生成答案，比单纯在 prompt 中硬编码工具说明更稳定、更可扩展。

## 9. 综合评价

从“项目方案”和“产品能力”角度看，模块二已经不是单点解析功能，而是一个结构完整、链路清晰、具有明显工程化深度的文档智能子系统。

它的核心价值不只是“把文档读出来”，而是：

1. **把多格式文档转成可理解、可验证、可追溯的数据对象。**
2. **把抽取结果沉淀为可继续问答、可继续同步、可继续入图谱的中间资产。**
3. **把前端工作台、后台抽取、智能助手和下游知识图谱串成一条连续工作流。**

如果后续继续优化，建议重点投入三件事：

1. 修复当前 provider preflight `503`，恢复“现场新跑”能力。
2. 将 XLSX 页面的“字段抽取结果 + 工作表预览 + 图表表达”做更严格的一致性校验。
3. 继续压缩 `bootstrap/` 过渡层，把重复 builder 逻辑进一步下沉到更标准的 services / core / repositories 分层中。
