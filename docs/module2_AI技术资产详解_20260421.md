# 模块二 AI 技术资产详解

## 1. 编写目的

本文档面向项目方案编写、系统汇报、后续维护与资产治理，系统梳理模块二中与人工智能能力直接相关的核心技术资产。本文聚焦以下四类内容：

1. Prompt 资产
2. 字段/语义规则库
3. 智能助手的 function calling 与回答契约资产
4. 模块二评测题库

本文不讨论模块二的全部业务功能，也不覆盖全部运行日志、缓存与临时文件，而是聚焦那些真正决定模块二 AI 行为质量、稳定性、可控性和可评测性的关键资产。

## 2. 总体结论

模块二并不是一个“模型训练型模块”，而是一个“文档智能推理型模块”。它的 AI 效果不是依赖本地微调训练实现的，而是依赖以下四层资产共同驱动：

1. 轻量、职责单一、可版本化的 Prompt 资产，用于控制字段抽取、表格抽取与 JSON 修复。
2. 独立于代码逻辑的字段命名与语义规则库，用于提高自动 schema 推断、字段标准化、字段筛选和噪声控制质量。
3. 面向智能助手的 function calling、意图规划、工具执行、回答契约与前端证据约束，用于把“大模型会说话”升级为“能稳定完成任务的文档智能体”。
4. 面向真实用户问题的评测题库，用于对 groundedness、澄清能力、边界表达、任务完成度和用户体验做回归验证。

从工程视角看，模块二最有价值的地方不只是“用了模型”，而是把 Prompt、规则、工具、回答规范和评测样本都做成了独立资产层，从而使系统具备持续优化能力，而不是只能依靠改一段提示词去碰运气。

## 3. 模块二 Prompt 资产

### 3.1 资产范围

模块二当前的核心 Prompt 资产位于 `backend/app/modules/module2/prompts/` 目录，主要包括三份：

1. 文本证据字段抽取系统提示词（`extract_fields.prompty`）
2. 表格证据字段抽取系统提示词（`extract_table_fields.prompty`）
3. JSON 结构修复系统提示词（`json_repair.prompty`）

对应的统一加载与版本管理代码位于 `backend/app/modules/module2/core/schema/prompt_assets.py`。

### 3.2 Prompt 资产清单

| 中文名称 | 对应文件 | 文件路径 | 主要职责 | 主要输入 | 输出约束 | 典型调用位置 |
| --- | --- | --- | --- | --- | --- | --- |
| 文本证据字段抽取系统提示词 | `extract_fields.prompty` | `backend/app/modules/module2/prompts/extract_fields.prompty` | 从带 `<ref id="...">` 的 markdown 上下文中抽取结构化字段 | 文本块、引用块、目标字段名 | 仅返回 JSON，且结果必须 grounded 到现有 `ref_id` | `backend/app/modules/module2/agent/graph.py` |
| 表格证据字段抽取系统提示词 | `extract_table_fields.prompty` | `backend/app/modules/module2/prompts/extract_table_fields.prompty` | 优先从结构化表格 JSON 中做字段抽取 | 表头、单元格、行列上下文 | 仅返回 JSON，且必须 grounded 到表格单元格 `ref_id` | `backend/app/modules/module2/agent/graph.py` |
| JSON 结构修复系统提示词 | `json_repair.prompty` | `backend/app/modules/module2/prompts/json_repair.prompty` | 将模型的非严格输出修复为一个可被解析的 JSON 对象 | 上一步不规范的模型输出 | 只允许返回一个合法 JSON 对象，不允许额外解释 | `backend/app/modules/module2/agent/graph.py` |

### 3.3 三份 Prompt 的职责分工

#### 3.3.1 文本证据字段抽取系统提示词（`extract_fields.prompty`）

这份 Prompt 的定位是“文本证据优先的字段抽取器”。它不是泛泛地要求模型“理解文本”，而是明确约束模型：

1. 输入是带 `ref_id` 的 markdown。
2. 返回值必须 grounded 到现有引用块。
3. 应优先匹配别名、同义表达、缩写、双语标签、附近的标签值对。
4. 对指标类字段，应优先依赖表头、表行、单位上下文，而不是凭语义大范围猜测。
5. 证据弱或冲突时返回 `null`，而不是编造答案。

这份 Prompt 的核心价值，在于它把“字段抽取”从一般性问答转成了“证据驱动的结构化提取任务”。

#### 3.3.2 表格证据字段抽取系统提示词（`extract_table_fields.prompty`）

这份 Prompt 的定位是“表格优先抽取器”。它特别强调：

1. 先看单元格，再看远处文本。
2. 优先利用表头、别名、单位、合并表头、行标签、汇总行。
3. 允许在同一行、同一列和分裂单元格中做有限重组。
4. 如果首个命中单元格是 `-`、空白、`N/A`、`null` 一类占位值，要继续向下寻找显式值。
5. grounding 不足时，必须返回 `null`。

这份 Prompt 对模块二非常关键，因为模块二面对大量统计公报、公告、Excel 派生文本、表格密集型文档。若没有这层表格专用 Prompt，字段抽取会明显退化成“泛文本匹配”，导致数值字段命中率下降。

#### 3.3.3 JSON 结构修复系统提示词（`json_repair.prompty`）

这份 Prompt 的职责很明确，不负责理解业务，只负责“把输出修成机器能吃的 JSON”。它的存在说明模块二在设计时已经意识到：

1. 模型在复杂抽取场景下可能输出不严格 JSON。
2. 前端与后端后续链路依赖严格结构化结果。
3. 与其在主 Prompt 中堆大量格式限制，不如单独拆出一个修复 Prompt 做末端收口。

这种设计避免了主抽取 Prompt 过度臃肿，也降低了格式问题对上游理解质量的干扰。

### 3.4 Prompt 资产的加载与版本化机制

`backend/app/modules/module2/core/schema/prompt_assets.py` 对模块二 Prompt 资产做了统一管理，具有以下几个特点：

1. 通过 `PROMPT_FILE_MAP` 将逻辑名映射到具体 `.prompty` 文件。
2. 通过 `load_prompt_assets()` 一次性加载全部 Prompt。
3. 对每份 Prompt 计算 `sha256` 摘要，形成可追踪版本。
4. 对所有 Prompt 内容再计算一个汇总 `version digest`，形成整体 Prompt 资产版本。
5. 通过 `lru_cache` 做只读缓存，避免运行期反复 IO。

这意味着模块二的 Prompt 不是“散落在代码字符串里”，而是正式的资产层。其价值在于：

1. 可以版本化。
2. 可以独立测试。
3. 可以在不改业务代码的前提下更新。
4. 可以作为质量回归时的变更边界。

### 3.5 模块二 Prompt 资产的设计特点

模块二的 Prompt 资产设计有三个非常明确的工程特征：

1. Prompt 职责单一。文本抽取、表格抽取、JSON 修复分开，不混在一份超级 Prompt 里。
2. Prompt 约束聚焦于证据与结构，而不是堆砌模板化语言。这种做法更不容易压死模型自身能力。
3. Prompt 与规则库配合，而不是互相替代。Prompt 决定抽取任务形态，规则库决定字段候选、命名约束与语义边界。

### 3.6 模块二字段抽取提示词的构建逻辑

模块二的字段抽取提示词，不是把一段固定提示词原样发给模型，而是采用“静态系统提示词 + 动态用户提示词 + 上下文预算控制 + 校验错误回灌”的构建方式。其核心逻辑如下。

#### 3.6.1 先装载三类底层提示词资产，再绑定到抽取运行时

在 `backend/app/modules/module2/agent/graph.py` 的 `ExtractionGraph.__init__()` 中，系统会先通过 `backend/app/modules/module2/core/schema/prompt_assets.py` 统一加载 Prompt 资产，再分别绑定为：

1. `_system_prompt`：文本证据字段抽取系统提示词
2. `_table_system_prompt`：表格证据字段抽取系统提示词
3. `_json_repair_system_prompt`：JSON 结构修复系统提示词

同时，系统还会记录 Prompt 资产整体版本、Prompt 名称列表和每份 Prompt 的哈希摘要。这意味着模块二的字段抽取提示词体系不只是“可调用”，而且是“可追踪、可回归、可审计”的。

#### 3.6.2 普通文本抽取提示词先做证据裁剪，再做动态拼装

普通字段抽取的核心入口在 `backend/app/modules/module2/agent/graph.py` 的 `extraction_node()`。这一阶段不会把整份 markdown 原文直接塞给模型，而是先调用 `_build_context()` 做证据裁剪，再拼装当前轮次的动态用户提示词。

动态用户提示词通常包含以下组成部分：

1. `Document Markdown`：经过裁剪后的文档上下文
2. `Target Schema`：本轮待抽取字段及其目标类型
3. `Fields requiring correction first`：需要优先修正的字段
4. `Table profile summary`：文档内表格结构摘要
5. `Field-to-table hints`：字段到表格的匹配提示
6. `Already extracted fields`：当前已抽取结果摘要
7. `Allowed ref_id candidates`：本轮允许引用的证据锚点范围
8. `Previous validation errors to correct`：上一轮校验错误
9. `Extraction rules`：别名识别、证据优先、证据不足返回 `null` 等规则
10. 最终 JSON 输出契约

因此，模块二普通文本抽取提示词的本质，不是“让模型自由理解文档”，而是“把本轮允许看的证据范围、必须修正的错误和必须遵守的结构一次性交代清楚”。

#### 3.6.3 `_build_context()` 控制提示词预算和证据相关性

`_build_context()` 会优先根据目标字段生成关键词，再从 markdown 中抽出 `<ref id="...">...</ref>` 证据块，按照命中度排序后，在提示词预算内保留高相关片段。

其关键控制参数包括：

1. `MODULE2_PROMPT_MAX_CHARS`
2. `MODULE2_PROMPT_MAX_REFS`
3. `MODULE2_PROMPT_FALLBACK_REF_LIMIT`

也就是说，模块二普通文本抽取提示词的构建，不是整篇原文直接投喂，而是先做“与目标字段相关的证据精排”，再进入 Prompt 拼装阶段。

#### 3.6.4 表格抽取提示词是另一条独立构建链

当文档中存在表格证据时，模块二会转入表格抽取链。此时系统先调用 `_build_table_context()` 把表格压缩成结构化 JSON，再拼装面向表格的动态用户提示词。

这一阶段的提示词通常包含：

1. `Table profile summary`
2. `Target Schema`
3. `Fields requiring correction first`
4. `Table context JSON`
5. `Allowed table ref_id candidates`
6. `Previous validation errors to correct`
7. 面向表头、行标签、单位、占位值处理的专门抽取规则
8. 严格 JSON 返回契约

这套构建逻辑的重点是把模型注意力收束到表头、列、行、单元格以及相邻结构关系上，而不是让模型用长文本语义去“猜”表格值。

#### 3.6.5 表格上下文采用渐进式收缩，而不是尾部截断

`_build_table_context()` 会按照“表数量 -> 行数 -> 列数 -> 表头元信息”的顺序逐步压缩表格 JSON，直到满足预算限制。其关键参数包括：

1. `MODULE2_TABLE_CONTEXT_MAX_TABLES`
2. `MODULE2_TABLE_CONTEXT_MAX_ROWS`
3. `MODULE2_TABLE_CONTEXT_MAX_COLS`
4. `MODULE2_TABLE_CONTEXT_MAX_HEADER_META`
5. `MODULE2_TABLE_CONTEXT_MAX_CHARS`

这种设计的工程含义很明确：在预算不足时，优先保住表格结构，再逐步缩减细节，而不是粗暴截断。

#### 3.6.6 校验错误会反向进入下一轮提示词

模块二字段抽取不是单轮固定提示词，而是“抽取 -> 校验 -> 错误回灌 -> 再抽取”的闭环。校验阶段会检查：

1. 必填字段是否缺失
2. `source_ref_id` 是否有效
3. `bbox` 是否完整
4. 字段类型是否匹配
5. 日期顺序和 schema 规则是否成立

一旦校验失败，错误信息会进入下一轮提示词中的 `Previous validation errors to correct`，相应字段也会进入 `Fields requiring correction first`。因此，模块二字段抽取提示词本身就是一个带反馈机制的动态系统。

#### 3.6.7 JSON 修复提示词承担末端结构收口职责

如果模型输出不是合法 JSON，模块二会启用 JSON 结构修复系统提示词，再额外构造一轮“只修复 JSON 结构、不重做语义理解”的修复提示词。该阶段会明确要求：

1. 把当前输出转换为一个合法 JSON 对象
2. 能保留的键值尽量保留
3. 无法安全修复时返回明确的兜底空结构

这一层的价值不在于增强语义能力，而在于保证模块二字段抽取链路在结构层面足够稳定，便于后续校验、前端展示和结果持久化。

### 4.3 `field_naming_rules_v1.json` 的定位

这份规则文件是模块二字段资产里最重要的一份。它并不是简单的“字段别名字典”，而是一个多层结构化命名知识库，主要承担以下职责：

1. 定义 `forbidden_aliases`，防止把 `result`、`value`、`content`、`name` 一类过泛词直接当字段名。
2. 定义多种文档模板，例如政府统计公报、医疗统计公报、环境监测报告、招聘表、临床数据集、疫情监测数据集、业务台账等。
3. 为每类模板配置 `match_any` 线索，使系统能从标题、前言或局部文本快速判断文档类型。
4. 提供模板回退配置、字段规则、自动候选字段与宏观标签控制。
5. 结合单位后缀、括号、百分比、比率、数量级信息，辅助生成更规范的字段键名。

这份规则本质上是模块二“字段标准化知识”的中心资产。

### 4.4 `field_naming.py` 的作用机制

`backend/app/modules/module2/core/schema/field_naming.py` 并不只是读 JSON，它还把规则加工成真正可执行的命名引擎。其主要功能包括：

1. 统一读取 `field_naming_rules_v1.json`。
2. 维护规则版本号 `FIELD_NAMING_VERSION`。
3. 处理括号、分隔符、单位后缀、百分比、比例、数量级等命名噪声。
4. 识别模板回退规则和自动候选规则。
5. 提供字段类型归一化能力，例如把 `int/integer` 归并为 `integer`，把 `float/number/decimal` 归并为 `number`。
6. 生成简化 ASCII key 作为字段键名回退。

因此，`field_naming_rules_v1.json` 负责提供知识，`field_naming.py` 负责把知识变成可执行的命名策略。

### 4.5 `schema_rule_assets.py` 的作用机制

`backend/app/modules/module2/core/schema/schema_rule_assets.py` 的作用是把其余五类规则库做成可缓存、可复用、可版本标识的只读资产。其特点包括：

1. 统一从 `assets/` 目录读取 JSON。
2. 用 `lru_cache` 避免重复加载。
3. 将 JSON 中的列表转成 `frozenset`、`tuple` 等稳定结构。
4. 对不同规则集返回标准化结构，便于后续流水线直接消费。
5. 通过 `schema_rule_versions()` 暴露规则版本摘要。

从系统设计上看，这一步非常关键。因为它把“规则文件”从纯静态资源变成了“受约束的数据资产接口”。

### 4.6 各规则文件的工程价值

#### 4.6.1 `schema_noise_rules_v1.json`

这份文件负责解决“抽出了一堆字段，但很多字段没价值”的问题。它主要控制：

1. 自动 schema 的英文停词。
2. 中文泛化词与精确泛化词。
3. 单位噪声词。
4. 日文精确泛化词。
5. 低价值结果词。
6. 启发式停止词。

这份规则的价值不是提高召回，而是提高“字段集合的可用性”。

#### 4.6.2 `field_type_rules_v1.json`

这份文件用于把字段从“看起来像字段”推进到“看起来是什么类型的字段”。它主要包含：

1. `date_tokens`
2. `integer_tokens`
3. `number_tokens`

其作用是减少后续 schema 设计与数据库建模阶段的类型混乱。

#### 4.6.3 `schema_selection_rules_v1.json`

这份文件负责控制自动 schema 选择策略，例如：

1. 可用的候选模板列表。
2. 表格/XLSX 重场景的最大字段数。
3. PDF 最大字段数环境变量名与默认值。
4. 候选池扩容倍数与上限。

它决定的不是字段内容本身，而是“系统最终保留多少字段、优先看多大的候选池”。

#### 4.6.4 `schema_semantic_rules_v1.json`

这份文件是模块二语义规则的主心骨，定义了：

1. 英文与中文的弱语义词。
2. 英文与中文的弱包含词。
3. 指标类 token。
4. 标识类 token。
5. 时间类 token。
6. 类别类 token。
7. 选择、闭包相关的阈值参数。

其核心作用是帮助系统判断：

1. 某个字段名是否太泛。
2. 某个字段更像指标、标识、时间还是类别。
3. 某些字段是否值得保留到最终 schema 中。

#### 4.6.5 `schema_coverage_profiles_v1.json`

这份文件是模板级 coverage 策略层。它定义：

1. `critical_fields`
2. `preferred_fields`
3. 文本场景下的目标字段数
4. 表格场景下的目标字段数
5. 规则冻结字段数

这使模块二不再以“一刀切”的方式抽字段，而是能根据文档类型决定“什么字段必须保、什么字段优先保、最终字段量控制在什么范围”。

### 4.7 规则库如何进入模块二主流程

在 `backend/app/modules/module2/services/extraction/foundation_builder.py` 中，模块二会在启动基础组件时统一加载：

1. `schema_noise_rules`
2. `field_type_rules`
3. `schema_selection_rules`
4. `schema_semantic_rules`
5. `schema_coverage_profiles`
6. `field_naming_version`

随后，这些资产被传入 schema pipeline、字段命名、候选筛选、自动 schema 推断和抽取主流程中。换言之，这些规则库不是“可有可无的配置文件”，而是模块二 schema 推断链路的基础依赖。

### 4.8 模块二规则资产的设计价值

模块二字段/语义规则库的价值，主要体现在以下几点：

1. 把字段命名知识从代码里抽离成可维护资产。
2. 把不同文档类型的 schema 习惯做成模板化知识，而不是让模型每次临场发挥。
3. 把噪声控制、语义分类、字段上限、关键字段优先级这些工程问题显式化。
4. 使自动 schema 推断具备“可解释、可调优、可回归”的基础。

## 5. 模块二助手的 function calling 与回答契约资产

### 5.1 资产范围

模块二助手并不是一个单纯“调用模型问答”的组件，而是一套由意图规划、工具定义、工具执行、回答规范、前端证据约束和失败兜底机制组成的智能体系统。其核心文件包括：

1. `backend/app/modules/module2/assistant_1/prompt_blocks.py`
2. `backend/app/modules/module2/assistant_1/answer_contracts.py`
3. `backend/app/modules/module2/assistant_1/response_planner.py`
4. `backend/app/modules/module2/assistant_1/task_policy.py`
5. `backend/app/modules/module2/assistant_1/tool_router.py`
6. `backend/app/modules/module2/assistant_1/responses_provider.py`
7. `backend/app/modules/module2/assistant_1/agent_runtime.py`

### 5.2 `prompt_blocks.py` 的定位

`prompt_blocks.py` 负责把模块二助手的系统级指令拼成一份完整指令块。它主要由以下几部分组成：

1. `core_instruction_block`
2. `session_context_block`
3. `turn_hint_block`
4. `build_assistant_instructions`

这份资产的核心价值在于：

1. 先定义角色，再定义证据边界，再定义当前轮次注意事项。
2. 可以按当前用户问题动态拼接 turn-level hint，而不是用一份死 Prompt 覆盖全部场景。
3. 可以嵌入前端上下文与证据 dossier，使回答和当前页面状态保持一致。

### 5.3 `answer_contracts.py` 的定位

`answer_contracts.py` 负责为不同 intent 定义回答契约。当前已覆盖的主要 intent 包括：

1. `capability`
2. `web_search`
3. `schema_design`
4. `sql_request`
5. `document_lookup`
6. `entity_extraction`
7. `document_summary`
8. `document_risk_review`
9. `general_method`
10. `missing_document`

其本质作用，是把“不同任务该如何回答”从模型自由发挥，升级为“受 intent 约束的回答规范”。例如：

1. `document_lookup` 强调必须核对行级证据，证据不足就明确写“current evidence not found”。
2. `entity_extraction` 强调结构化输出与缺失字段标记。
3. `schema_design` 强调尽量输出表、字段、索引、DDL 一类可落地结果。
4. `sql_request` 强调先返回可审查 SQL 草案，再给安全确认提示。

### 5.4 `response_planner.py` 的定位

`response_planner.py` 负责把用户问题转换为一份明确的执行计划 `Assistant1ResponsePlan`。这份计划至少包含：

1. 是否使用工具
2. 文本冗长度
3. 输出 token 上限
4. reasoning effort
5. 可用工具名
6. intent
7. 是否必须澄清
8. 澄清原因
9. tool choice
10. 是否要求必须发生 tool call
11. 主工具名
12. 工具执行模式

换句话说，这里负责的不是“生成答案”，而是“决定这道题应该怎么走链路”。

### 5.5 `task_policy.py` 的定位

`task_policy.py` 提供了 function calling 的三张关键策略表：

1. `TOOL_REQUIRED_INTENTS`
2. `PRIMARY_TOOL_BY_INTENT`
3. `TOOL_FIRST_INTENTS`

这三张表的价值非常高：

1. 明确哪些意图必须用工具，防止模型在需要证据的场景里直接自由回答。
2. 明确每个 intent 的主工具，便于 `tool_choice` 和失败兜底逻辑统一。
3. 明确哪些意图适合 `tool_first`，即先拉证据、再做 grounded synthesis。

### 5.6 `tool_router.py` 的定位

`tool_router.py` 是模块二 function calling 的工具总线。它同时承担两类职责：

1. 定义工具接口
2. 执行工具分发

当前模块二助手的工具定义包括：

| 工具名 | 核心职责 | 典型场景 |
| --- | --- | --- |
| `search_knowledge_base_grouped` | 分组检索知识库证据，尽量按年份或版本聚合 | 年份对比、版本对比、概览总结、趋势解释 |
| `search_knowledge_base` | 检索当前文档或指定文件的知识证据 | 文档查值、字段核对、图表说明、页级内容问答 |
| `ingest_document` | 构建并持久化文档知识工件 | 当前文件尚未入知识库时做预处理 |
| `web_search_tavily` | 查询公网与外部官方信息 | 最新信息、官方来源、文档外知识补充 |
| `inspect_database_schema` | 查看 PostgreSQL 实时 schema | schema 设计、SQL 生成前的真实结构对齐 |
| `design_schema_draft` | 生成数据库 schema 草案 | 文档抽取结果落库建模 |
| `draft_sql_from_nl` | 将自然语言请求转成 SQL 草案 | NL2SQL |
| `execute_sql_with_audit` | 带审计执行 SQL | 确认后执行写入、DDL 或查询 |

这说明模块二助手的 function calling 不是装饰性的，而是同时打通了：

1. 文档检索
2. 文档入库
3. 外部搜索
4. schema 设计
5. SQL 草拟
6. SQL 审计执行

### 5.7 `responses_provider.py` 的定位

`responses_provider.py` 是模型接口抽象层。它的价值不在于“调一下 API”，而在于提供了：

1. Responses 风格与 Chat Completions 风格的兼容抽象。
2. tool arguments 的标准化解析。
3. SSE 流式事件解析。
4. response_id 与 previous_response_id 的上下文续接。
5. 工具输出转消息项的桥接。

因此，这一层保证了模块二助手的 function calling 不是绑死在某一种调用协议上。

### 5.8 `agent_runtime.py` 的执行链路

`agent_runtime.py` 是模块二助手最重要的执行编排层。其 function calling 逻辑可概括为以下七步：

1. 先根据 `response_planner` 生成本轮 `response_plan`。
2. 基于 `prompt_blocks` 与 `answer_contracts` 生成本轮 instructions。
3. 调用 `responses_provider.complete()` 发起初始请求。
4. 如果当前 intent 要求必须用工具，但模型没有产生 function call，则进入 `_recover_missing_required_tool()`。
5. 在恢复逻辑中，先尝试 `tool_choice="required"` 重试；若仍失败，则走人工主工具执行或数据库兜底执行。
6. 对于 `tool_first` intent，会直接 `_run_primary_tool_manually()`，拿到 grounding result 后再做 `_complete_grounded_synthesis()`。
7. 最后再统一做 answer finalize，输出面向前端的最终回答。

这条链路说明模块二 function calling 的设计已经具备以下特征：

1. 有正常路径。
2. 有 required-tool 重试路径。
3. 有 manual tool fallback 路径。
4. 有 grounded synthesis 路径。
5. 有数据库意图专门兜底路径。

这比单纯依赖模型“自己记得调工具”稳定得多。

### 5.9 模块二回答契约的实际意义

回答契约资产的价值不在于限制模型表达，而在于：

1. 把不同意图的最低交付标准固定下来。
2. 防止文档查值场景下出现“编合理答案”的幻觉。
3. 防止数据库设计场景下输出空泛建议。
4. 防止 SQL 场景下跳过审查与确认。
5. 防止“没文档也假装看过文档”的越界回答。

从产品角度看，这一层是“把模型能力变成产品能力”的关键。

### 5.10 模块二智能助手提示词的构建逻辑

模块二智能助手的提示词构建逻辑，与字段抽取链不同。它本质上是一套“先做任务规划，再装配提示词，再决定是否 function calling，最后做 grounded synthesis”的执行体系。

#### 5.10.1 先做响应规划，再决定如何构建提示词

入口在 `backend/app/modules/module2/assistant_1/response_planner.py`。系统会先根据用户问题判断：

1. 当前意图是什么
2. 是否必须调用工具
3. 可用工具有哪些
4. 是否需要澄清
5. 输出应该多短或多长
6. 当前轮次是 `model_first` 还是 `tool_first`

因此，模块二智能助手的提示词不是“先写好，再统一套用”，而是先有 `response_plan`，再按计划进行提示词装配。

#### 5.10.2 系统指令由多个提示词块顺序拼装而成

`backend/app/modules/module2/assistant_1/prompt_blocks.py` 中的 `build_assistant_instructions()` 会把多个提示词块拼成当前轮次的完整系统指令，主要包括：

1. `core_instruction_block`：角色、风格、证据边界、禁止暴露内部 ID 与工具链路
2. `session_context_block`：当前会话是否已绑定默认文档
3. `answer_contract`：当前意图对应的回答契约
4. `frontend_context_block`：前端当前活动文档快照
5. `frontend_evidence_dossier_block`：前端整理好的证据 dossier
6. `turn_hint_block`：本轮附加要求，例如是否必须澄清、是否偏时间对比、是否要求 JSON 输出

也就是说，模块二智能助手的提示词不是单一长 Prompt，而是“总角色约束 + 会话上下文 + 意图级回答契约 + 前端证据 + 本轮提示”的组合体。

#### 5.10.3 回答契约会按意图切换回答边界和输出方式

`backend/app/modules/module2/assistant_1/answer_contracts.py` 会根据当前 intent 注入不同的回答规则。例如：

1. `document_lookup` 强调必须做精确证据核验，证据不足就直说当前证据未找到
2. `entity_extraction` 强调结构化输出和缺失字段标记
3. `schema_design` 强调优先交付表结构、字段、索引或 DDL
4. `sql_request` 强调先给可审查 SQL，再给简洁的安全确认提示
5. `web_search` 强调优先给结论和来源

这意味着模块二智能助手的提示词构建，不只是“写回答内容”，还包括“在不同任务下必须以什么产品姿态交付回答”。

#### 5.10.4 前端快照与前端证据包会直接进入提示词

`backend/app/modules/module2/assistant_1/frontend_grounding.py` 会把前端可见状态清洗成两类提示词输入：

1. 前端活动文档快照
2. 前端证据 dossier

其中通常包含：

1. 当前文件名和文件哈希
2. 摘要
3. top fields
4. 表头字段
5. 图表关键点
6. 年份覆盖和季度覆盖信息
7. 必须避免臆断的证据策略

这一步的价值在于，让智能助手优先复用前端已经稳定展示的事实，而不是每一轮都重新“猜用户现在看到什么”。

#### 5.10.5 function calling 的工具定义本身也是提示词的一部分

`backend/app/modules/module2/assistant_1/tool_router.py` 中的工具 schema，会与模型一起传入，成为 function calling 决策的提示词输入。这里不仅定义了工具名，还定义了：

1. 工具在什么任务下应该被调用
2. 每个参数的意义是什么
3. 参数有哪些取值范围和约束

配合 `backend/app/modules/module2/assistant_1/task_policy.py` 中的：

1. `TOOL_REQUIRED_INTENTS`
2. `PRIMARY_TOOL_BY_INTENT`
3. `TOOL_FIRST_INTENTS`

系统就能把“工具能力”转化为“模型可理解的调用决策边界”。

#### 5.10.6 工具结果不会直接裸返回，而是进入二次综合提示词

当工具执行完成后，`backend/app/modules/module2/assistant_1/agent_runtime.py` 会构造 grounded synthesis 提示词，要求模型：

1. 只基于已整理的证据回答原始问题
2. 不暴露工具名、函数调用、检索链路和内部 ID
3. 证据不足时直接说明还缺什么
4. 针对 `web_search`、`document_summary`、`document_risk_review`、`document_lookup` 等意图采用不同的证据解释方式

这一阶段本质上是第二轮提示词构建。第一轮提示词用于“决定怎么查”，第二轮提示词用于“决定怎么把查到的证据组织成面向用户的自然回答”。

#### 5.10.7 当模型没有调用应调工具时，系统会重构提示词并强制补救

如果某些意图按策略必须调用工具，但模型没有给出 function call，模块二不会直接放弃，而是进入补救链路：

1. 先把 `tool_choice` 提升为 `required` 再重试一次
2. 若仍失败，则根据 intent 进入人工主工具执行或数据库兜底执行
3. 拿到结果后再走 grounded synthesis

这说明模块二智能助手的提示词构建逻辑，不是“交给模型临场发挥”，而是“提示词引导 + 策略约束 + 运行时兜底”的组合式架构。

## 6. 模块二评测题库

### 6.1 资产位置与定位

模块二评测题库位于：

`docs/superpowers/specs/2026-04-10-module2-assistant-eval-question-bank.md`

这份文件不是一般性的测试说明，而是一份面向真实用户视角的评测资产。它的目标不是故意为难模型，而是系统评估模块二智能助手在真实使用场景中的表现。

### 6.2 题库结构

这份题库至少包含以下几个结构层：

1. 评测目标
2. 使用方式
3. 当前基线文档
4. 高优先级题集
5. 扩展题集
6. 信任与溯源题集
7. 错误与缺失题集
8. 通过标准
9. 记录模板

它已经不是零散问题清单，而是一份可持续回归使用的评测规范。

### 6.3 评测维度

从题库内容可归纳出模块二主要评测以下维度：

1. 任务完成度
2. groundedness
3. 澄清能力
4. 边界表达与可信表达
5. 实用价值
6. 首答速度与交互体验

这几个维度和模块二当前的产品目标是高度一致的，尤其适合评估“文档型智能助手”而不是通用聊天机器人。

### 6.4 题型设计特点

题库中的题型具有明显的工程价值：

1. 有极短路径问题，例如“当前文档的统计年份是什么，只回数字”，用于测试短路能力与最小回答。
2. 有摘要与关键字段结合问题，用于测试概括与抽取协同能力。
3. 有模糊提问问题，用于测试是否会直接澄清而不是胡猜。
4. 有溯源问题，用于测试模型是否能说明信息来自哪一类证据。
5. 有缺失信息问题，用于测试系统是否会编造不存在的字段。
6. 有下游建模问题，用于测试回答是否能连接到数据库建模或知识图谱建模任务。

### 6.5 题库的工程意义

这份题库对模块二的价值主要有四点：

1. 它把“用户觉得好不好用”拆成了可观察、可记录的问题集合。
2. 它可以直接作为回归集，验证改 Prompt、改检索、改前端上下文、改 warning 文案后是否真的变好。
3. 它为后续构建多轮对话评测集、偏好数据集和高价值 golden cases 提供了基础模板。
4. 它让模块二的优化不再依赖主观印象，而能围绕明确题项迭代。
